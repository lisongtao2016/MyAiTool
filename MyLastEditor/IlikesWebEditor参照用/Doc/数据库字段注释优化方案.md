# 数据库字段注释优化方案

## 概述
根据ai_rule.md规则要求，数据库表字段必须有中文注释。由于SQLite不支持字段注释（COMMENT），本方案提供两种实现方式：
1. **文档化注释**：创建本文档记录所有字段的中文注释
2. **注释表方案**：创建单独的注释表，通过外键关联（可选）

## 优化建议

### 1. 字段长度优化
- **Username**: 100 → 50（用户名通常不超过50字符）
- **Email**: 255 → 100（邮箱地址通常不超过100字符）
- **DisplayName**: 100 → 50（显示名称通常较短）
- **Role**: 50 → 20（角色名称通常很短）
- **Name**: 100 → 80（项目名称通常较短）
- **Description**: 500 → 300（描述可以适当缩短）
- **Title**: 255 → 200（标题通常不超过200字符）
- **Subtitle**: 500 → 300（副标题可以适当缩短）
- **HotTags/ShareTo**: 500 → 200（标签和分享对象可缩短）

### 2. SQLite限制说明
- SQLite不支持TINYINT、SMALLINT等类型，INTEGER已是最小整数类型
- SQLite不支持字段注释（COMMENT），需通过其他方式实现
- SQLite的NVARCHAR实际上存储为TEXT，长度限制仅由应用层控制

### 3. 实施策略
**方案A：文档化注释（推荐）**
- 优点：无风险，不改变现有结构
- 缺点：注释不在数据库中，需查阅文档

**方案B：创建注释表**
```sql
CREATE TABLE IF NOT EXISTS ColumnComments (
    TableName NVARCHAR(50) NOT NULL,
    ColumnName NVARCHAR(50) NOT NULL,
    Comment NVARCHAR(200) NOT NULL,
    PRIMARY KEY (TableName, ColumnName)
);
```
- 优点：注释存储在数据库中，可编程访问
- 缺点：增加复杂性，需要维护

**方案C：使用SQLite扩展**
- 使用sqlite3的扩展功能支持注释
- 需要编译自定义版本，不推荐

## 时间字段命名建议
ai_rule.md要求使用`create_time`和`update_time`，但当前使用`CreatedDate`和`ModifiedDate`。建议：
1. **维持现状**：已广泛使用，修改成本高
2. **新增表遵循新规范**：新表使用`create_time`和`update_time`

## 触发器示例（自动更新ModifiedDate）
```sql
-- 为EditorContents表创建触发器
CREATE TRIGGER IF NOT EXISTS update_editorcontents_modified
AFTER UPDATE ON EditorContents
BEGIN
    UPDATE EditorContents 
    SET ModifiedDate = CURRENT_TIMESTAMP 
    WHERE Id = NEW.Id;
END;

-- 为Projects表创建触发器
CREATE TRIGGER IF NOT EXISTS update_projects_modified
AFTER UPDATE ON Projects
BEGIN
    UPDATE Projects 
    SET ModifiedDate = CURRENT_TIMESTAMP 
    WHERE Id = NEW.Id;
END;
```

## 结论
1. **建议采用方案A**：创建本文档记录字段注释，成本最低，风险为零
2. **字段长度优化可选择性实施**：考虑到SQLite的实际存储方式，长度优化对存储空间影响有限
3. **触发器可添加**：自动更新时间字段，提高数据一致性
4. **新表遵循ai_rule.md规则**：新创建的表严格按规则设计
